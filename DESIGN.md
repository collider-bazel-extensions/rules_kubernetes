# rules_kubernetes — Design Document

## Goals

`rules_kubernetes` provides hermetic, parallel-safe Kubernetes API servers for
Bazel test targets. The design is driven by three constraints:

1. **No Docker, no root.** The package must work in standard CI sandboxes where
   neither Docker nor elevated privileges are available. This rules out kind and
   vanilla k3s and scopes the target to `kube-apiserver` + `etcd`.
2. **Full `--jobs` parallelism.** Each test must own an independent API server
   on a unique port with a UUID-based namespace — no shared state between tests.
3. **Zero test-code changes.** Tests receive a standard `KUBECONFIG` path and
   `KUBE_NAMESPACE` name; they connect as if to any Kubernetes cluster.

---

## Scope

`rules_kubernetes` targets **controller and operator authors** — the dominant
Bazel+Kubernetes use case. Tests exercise code that talks to the Kubernetes API:
custom controllers, admission webhooks, CRD validation, RBAC, operator
reconciliation loops.

It does **not** target full end-to-end cluster tests where actual containers must
run. That workload requires a kubelet and a container runtime; it is better
served by dedicated e2e tools (Chainsaw, kuttl, Testkube) that assume a
pre-existing cluster.

### What you can test

- Controllers and operators (reconcile loops, watches, finalizers)
- Admission webhooks (validating, mutating)
- CRD validation (structural schemas, CEL rules)
- RBAC policies (impersonation, SubjectAccessReview)
- Any code that calls `client-go`, `controller-runtime`, or `k8s.io/client-go`

### What you cannot test

- Pod scheduling or actual container execution
- Node lifecycle, kubelet, CNI plugins
- Services routing real traffic to pods
- Anything that requires a running kubelet

## High-level architecture

```
MODULE.bazel / WORKSPACE
        │
        ▼
  extensions.bzl / repositories.bzl     ← fetch or symlink kube-apiserver + etcd
        │
        ▼
  kubernetes_binary  (private/binary.bzl)   ← platform-agnostic binary target
        │                                       carries kube-apiserver + etcd paths
        ▼
  kubernetes_manifest  (private/manifest.bzl)  ← validated YAML manifests (CRDs, RBAC)
        │
        ▼
  kubernetes_controller  (private/controller.bzl)  ← controller binary + manifest
        │
        ├────────────────────────────────────────────────┐
        ▼                                                ▼
  kubernetes_test macro  (private/test.bzl)    kubernetes_server rule  (private/server.bzl)
    ├── <name>_inner — real test binary          long-running server binary
    └── <name>       — _k8s_launcher_test               │
              │                                         ▼
              └──────────────┐             kubernetes_health_check (private/server.bzl)
                             │               file-exists health probe
                             ▼
                        launcher.py
                  ┌──────────┴──────────┐
       RULES_K8S_MODE=test   RULES_K8S_MODE=server
                  │                     │
          _start_apiserver()    _start_apiserver()
                  │                     │
        _start_controller()    write kubeconfig + env file
                  │                     │
          os.execve(test)       signal.pause()
                                SIGTERM → stop
```

## Provider chain

```
KubernetesBinaryInfo          paths to kube-apiserver and etcd; all_files depset
  │
  └─► KubernetesManifestInfo  YAML files to apply (CRDs, RBAC, etc.);
        │                     ordered depset; carries KubernetesBinaryInfo
        │
        └─► KubernetesControllerInfo   controller executable + runfiles;
                                       carries KubernetesManifestInfo
```

`kubernetes_test` and `kubernetes_server` both accept a `controller` label and
receive the full binary+manifest chain transitively. `controller` is optional —
a test that only needs the API server (e.g., to test a client library) can omit
it and pass the binary directly.

## Binary acquisition

Two binaries are required: `kube-apiserver` and `etcd`. Both are acquired via
the same two-mode interface as rules_pg and rules_temporal.

### Downloaded tarballs (`kubernetes.version()`)

`_k8s_binary_repo` calls `rctx.download_and_extract` to fetch versioned
`kube-apiserver` and `etcd` binaries. The canonical download source is the
`envtest-bins` tarballs published by `kubernetes-sigs/controller-tools` at:

```
https://github.com/kubernetes-sigs/controller-tools/releases/download/
    envtest-v<version>/envtest-v<version>-<os>-<arch>.tar.gz
```

The tarball extracts to `controller-tools/envtest/` — `strip_prefix` is set to
`"controller-tools/envtest"` so the binaries (`kube-apiserver`, `etcd`,
`kubectl`) land at the repo root.

SHA-256 checksums are stored in `_K8S_VERSIONS` in `extensions.bzl`, a block
generated by `tools/update_checksums.sh`. controller-tools publishes only a
SHA-512 per tarball (`<asset>.sha512`); the script downloads each tarball,
checks it against that SHA-512, and pins its SHA-256. `--check` re-verifies
without writing.

### System binaries (`kubernetes.system()`)

`_k8s_system_binary_repo` symlinks host-installed binaries into an external
repo. Auto-detection at `bazel fetch` time:

1. `command -v kube-apiserver` — PATH lookup.
2. Common locations: `/usr/local/kubebuilder/bin`, `/usr/local/bin`,
   `/usr/bin`, and `$HOME/.local/kubebuilder/bin` (read from the repository
   rule environment at fetch time).

If either binary cannot be found, the build fails immediately with a clear error
and a suggested install command (`setup-envtest use <version>`).

Both modes produce a repo named `k8s_<version>_<platform>` (e.g.,
`k8s_1_35_linux_amd64`) exposing `kube-apiserver` and `etcd` as runfiles.

### Versions and selection (v0.4)

`private/versions.bzl` holds `SUPPORTED_VERSIONS` (1.29, 1.35, 1.36, 1.37),
`DEFAULT_VERSION` (1.35) and `PLATFORMS` (linux and darwin, amd64 and
arm64). `//:BUILD.bazel` generates one `k8s_<minor>` `kubernetes_binary` per
version from those lists, each a `select()` over its four platform repos;
`//:k8s_default` aliases the default.

- **Per-target selection.** `kubernetes_test` and `kubernetes_server` take
  `k8s_version` and map it to `//:k8s_<minor>` (`binary_label()`), failing at
  loading time on an unsupported version. `kubernetes_server` is therefore a
  macro over a private `_kubernetes_server` rule, as `kubernetes_test`
  already was. A rule-level `k8s_version` attribute would need every version's
  binary as an implicit dependency, which fetches every tarball.
- **Which minors.** 1.35/1.36/1.37 match rules_kind v0.2.0, so a consumer's
  envtest-level and kind-level tests can use the same Kubernetes minor
  (rules_kubernetes#3). 1.29 (end of life) stays for consumers who pin it.
  The default moved from 1.29 to 1.35 in v0.4.0, as in rules_kind.
- **One envtest release per minor.** The newest controller-tools envtest
  release for each minor at the time (1.29.0, 1.35.0, 1.36.2, 1.37.0).
  controller-tools doesn't publish every Kubernetes patch.
- **Repo dedup.** rules_kubernetes's own `MODULE.bazel` (non-dev) declares
  `kubernetes.version()` for every supported version, because its BUILD file
  refers to all of those repos. Through v0.3.0 a consumer that also declared
  a version got "A repo named k8s_1_29_linux_amd64 is already generated by
  this module extension". The extension now creates each repo once, taking
  the root module's tags first, so a root `kubernetes.system(["1.35"])`
  replaces the download for that version.

### Runnable kubectl (v0.5)

`//:kubectl_<minor>` is a `kubernetes_tool` (`private/tool.bzl`) over
`//:k8s_<minor>`; `//:kubectl` aliases the default. `kubernetes_binary` stays
a non-executable provider target: making it executable would have to pick
one of its three binaries. `kubernetes_tool` writes a bash wrapper from
`private/tool.sh.tmpl` whose only runfile is the chosen binary:

- It finds the runfiles tree through `$0.runfiles` (`bazel run`, or a tool in
  an action) or `$RUNFILES_DIR` (as `data` of a test), and makes it absolute
  before changing directory.
- It then changes to `$BUILD_WORKING_DIRECTORY` when set, so relative paths
  in the arguments resolve from where `bazel run` was invoked rather than
  from the runfiles tree, and `exec`s the binary.

A plain symlink as the executable would run kubectl from the runfiles
directory, where `-f ./x.yaml` doesn't resolve.

### Release archive

`.gitattributes` marks `tests/` `export-ignore`, so the GitHub tag tarball
(what `archive_override` fetches) has no packages that load dev-only modules
and `@rules_kubernetes//...` loads for consumers. `REPO.bazel`
`ignore_directories` was not used: it applies when rules_kubernetes is the
main repository too, which would hide `//tests/...` from its own CI.
`git_override` clones the repository, `tests/` included.

## TLS bootstrap

`kube-apiserver` requires TLS. The launcher generates ephemeral credentials at
test runtime — no pre-baked certs in the repository:

```
_bootstrap_tls(pki_dir)
  ├── generate CA key + self-signed cert           (ca.key, ca.crt)
  ├── generate server key + CSR                    (server.key, server.csr)
  ├── sign server cert with CA                     (server.crt)
  ├── generate client key + CSR                    (client.key, client.csr)
  └── sign client cert with CA                     (client.crt)
```

All files written to `$TEST_TMPDIR/<name>.k8s/pki/`. The launcher uses `openssl`
subprocess calls. The generated kubeconfig references these paths and is
written to `$TEST_TMPDIR/<name>.kubeconfig` (see Per-cluster paths).

`kube-apiserver` is started with:

```
--tls-cert-file     $TEST_TMPDIR/<name>.k8s/pki/server.crt
--tls-private-key-file $TEST_TMPDIR/<name>.k8s/pki/server.key
--client-ca-file    $TEST_TMPDIR/<name>.k8s/pki/ca.crt
```

The client cert is written into the kubeconfig as `client-certificate` /
`client-key` with the CA as `certificate-authority`.

## `kubernetes_manifest` rule

The `postgres_schema` analogue for Kubernetes. Declares YAML manifest files
(CRDs, RBAC, Namespaces, ConfigMaps) to apply to the API server before the
controller starts and before the test binary runs.

```python
kubernetes_manifest(
    name = "my_crds",
    srcs = glob(["config/crd/*.yaml"]),
    # Files applied in listed order via `kubectl apply -f`.
    # Use numeric prefixes for deterministic ordering: 001_crd.yaml, 002_rbac.yaml.
)
```

The launcher applies manifests in order via `kubectl apply -f <file>` after the
API server is ready and before starting the controller. Failures surface
immediately with the full `kubectl` output printed.

### Analysis-time validation

`kubernetes_manifest` validates at analysis time:
- `srcs` must not be empty.
- All files must have a `.yaml` or `.yml` extension.

Runtime YAML parse errors surface from `kubectl apply` output.

## `kubernetes_controller` rule

Declares a controller binary and links it to a manifest set. Produces a
`KubernetesControllerInfo` provider.

```python
kubernetes_controller(
    name              = "my_controller",
    controller_binary = "//cmd/controller",   # required: a *_binary target
    manifests         = ":my_crds",           # optional: kubernetes_manifest
)
```

Analysis-time validation:
- `controller_binary` must be present (label, not a string).

The controller is started by the launcher after manifests are applied and before
the worker-ready poll. It inherits `KUBECONFIG`, `KUBE_NAMESPACE`, and any
extra env vars declared in the `kubernetes_test` target.

## `kubernetes_test` macro

Expands into two targets, identical in structure to `temporal_test`:

- **`<name>_inner`** — the bare test binary. Tagged `manual`.
- **`<name>`** — a `_k8s_launcher_test` rule that wraps the inner binary.

### Launcher lifecycle (test mode)

```
read K8S_MANIFEST (JSON)
  ↓
claim $TEST_TMPDIR/<name>.claim  [exit 1, naming both labels, if a live launcher holds it]
  ↓
resolve runfile paths
  ↓
ensure execute bits on kube-apiserver, etcd, kubectl, controller binary
  ↓
allocate TCP ports for kube-apiserver (API) and etcd (peer + client)
  ↓
generate UUID namespace  (k8s-test-<12-hex>)
  ↓
take a server slot (RULES_K8S_MAX_SERVERS; see Launcher budgets and admission)
  ↓
_bootstrap_tls()  → $TEST_TMPDIR/<name>.k8s/pki/ + $TEST_TMPDIR/<name>.kubeconfig
  ↓
start etcd  [--unsafe-no-fsync by default; retry on port conflict, up to 5 attempts]
  ↓
_wait_etcd_ready: TCP open + etcd health endpoint (RULES_K8S_ETCD_READY_TIMEOUT, 15 s)
  ↓
start kube-apiserver  [retry on port conflict]
  ↓
_wait_apiserver_ready: TCP open + /readyz HTTP check (RULES_K8S_APISERVER_READY_TIMEOUT, 45 s)
  ↓
kubectl apply manifests in order (if kubernetes_manifest provided)
  ↓
kubectl create namespace <uuid-namespace>
  ↓
start controller subprocess (KUBECONFIG + KUBE_NAMESPACE set)  [if controller provided]
  ↓
_wait_controller_ready: poll until controller's leader-election lease appears
  or configurable readiness probe passes
  ↓
os.execve(test_binary, env={KUBECONFIG, KUBE_NAMESPACE, KUBE_API_SERVER})
```

Cleanup is handled by `atexit` handlers for `etcd_proc`, `apiserver_proc`, and
`controller_proc`. Bazel removes `$TEST_TMPDIR` after each test run. The
server slot's fd survives the `execve`, so the test binary, etcd and
kube-apiserver hold the slot until they have all exited.

### Environment variables injected

| Variable           | Example value                    | Description                        |
|--------------------|----------------------------------|------------------------------------|
| `KUBECONFIG`       | `$TEST_TMPDIR/<name>.kubeconfig` | Path to per-test kubeconfig        |
| `KUBE_NAMESPACE`   | `k8s-test-abc123def456`          | Isolated per-test namespace        |
| `KUBE_API_SERVER`  | `https://127.0.0.1:54321`        | API server address                 |
| `KUBECTL`          | `/path/to/kubectl`               | Absolute path to kubectl binary    |

`KUBECTL` is set because `kubectl` is not on `$PATH` in the Bazel sandbox;
test scripts must use `"$KUBECTL"` rather than relying on PATH.

## Port allocation

Three ports are needed per test: one for `kube-apiserver`, two for `etcd`
(client and peer). All three are allocated via `socket.bind(('127.0.0.1', 0))`
before any process starts. Sockets are closed just before the processes start.
Up to five retries handle the rare TOCTOU race; only port-binding conflicts
trigger a retry.

---

## Namespace isolation

Each `kubernetes_test` creates a UUID namespace (`k8s-test-<12 hex chars>`) at
runtime via `kubectl create namespace`. This guarantees:

- No resource bleeds between tests even with identical resource names.
- Tests are safe to run in parallel with `--jobs`.

The namespace name is injected as `KUBE_NAMESPACE`. Tests should scope all
resource creation to this namespace.

## `kubernetes_server` rule

Long-running API server for use as an `itest_service` in `rules_itest`. Uses
the same launcher with `RULES_K8S_MODE=server`. In server mode:

```
allocate ports → _bootstrap_tls → start etcd → start kube-apiserver
  ↓
kubectl apply manifests (if provided)
  ↓
kubectl create namespace <uuid>
  ↓
write $TEST_TMPDIR/<name>.env atomically   ← readiness signal
  ↓
install SIGTERM + SIGINT handlers
  ↓
signal.pause()
```

### Server env file format

```
KUBECONFIG=/tmp/.../kubeconfig
KUBE_NAMESPACE=k8s-test-abc123def456
KUBE_API_SERVER=https://127.0.0.1:54321
KUBECTL=/path/to/kubectl
```

`KUBECTL` is the absolute path to the kubectl binary used by the server. Tests
that source this env file can use `"$KUBECTL"` directly without kubectl being
in `$PATH`.

### `kubernetes_health_check`

Exits 0 iff `$TEST_TMPDIR/<server-name>.env` exists. Identical pattern to
`temporal_health_check` and `pg_health_check`.

## `kubernetes_test` vs `kubernetes_server` — when to use which

| Scenario | Use |
|---|---|
| Unit / integration test for a single controller | `kubernetes_test` |
| Multi-service test (HTTP API + controller + K8s) | `kubernetes_server` + `itest_service` |
| `bazel test` with per-target isolation | `kubernetes_test` |
| Shared API server across multiple services | `kubernetes_server` |

## Phase 2 — kwok integration

A `kubernetes_node_sim` optional extension adds `kwok` as a fourth binary,
enabling simulated node and pod lifecycle:

```python
kubernetes_node_sim(
    name    = "my_nodes",
    server  = ":my_apiserver",   # kubernetes_server or kubernetes_test worker
    count   = 10,                # number of simulated nodes
)
```

The launcher starts `kwok` after `kube-apiserver` is ready. Tests that need
to observe pod scheduling or node conditions wire in this extension.

This is intentionally deferred to Phase 2 — it adds a third binary and a more
complex readiness protocol. The base rules are useful without it.

## Server-side apply (v0.2.0)

`kubernetes_manifest`'s launcher applies each YAML via `kubectl apply --server-side --force-conflicts`. Server-side apply stores field-owner state on the apiserver rather than in the `kubectl.kubernetes.io/last-applied-configuration` annotation that client-side apply uses — that annotation has a hard 256KB size limit, so any single CRD whose encoded form exceeds it (CNPG `Cluster`, Argo Workflows full CRD set, etc.) fails client-side apply with `metadata.annotations: Too long`.

Server-side apply is GA and recommended since k8s 1.22; envtest's apiserver fully supports it. `--force-conflicts` makes the rule the field manager unconditionally, which is the right default since rules_kubernetes is the source of truth for the manifests it applies — taking over fields from a prior client-side apply (or an earlier rules_kubernetes apply with a different field manager) is intended behavior.

## Launcher budgets and admission (v0.6, #5)

Under host load (a 16-core host at load 100–600 running kind clusters and
several Bazel servers), envtests failed for three separate reasons. Each has
its own knob, read by `_load_config()` before the launcher reads its manifest.
An invalid value is a `ConfigError`: the launcher prints
`[rules_kubernetes] ERROR: <VAR>='<value>': expected …` and exits 1, with no
traceback and before anything starts. A typo in a budget therefore fails the
test instead of silently running with the default.

### Readiness timeouts

`RULES_K8S_ETCD_READY_TIMEOUT` (15 s) and `RULES_K8S_APISERVER_READY_TIMEOUT`
(45 s) replace the constants in `_wait_etcd_ready` and
`_wait_apiserver_ready`. The values are positive, finite seconds; fractions
are allowed. The defaults are unchanged. Measured on v0.4.0: apiserver ready
in 3.4–7 s at load 25–36, and 13.8–17.5 s with 24 starting at once at load
80–106. 45 s already covers that. The knob is for hosts that are worse
still, and the timeout message names the variable. The slot wait (below)
comes before these clocks start, so it never counts against them.

### etcd `--unsafe-no-fsync`: on by default

`RULES_K8S_ETCD_UNSAFE_NO_FSYNC` defaults to `1`; `0` opts out.

- **Why it is safe.** fsync only matters when a crash must leave the data
  dir recoverable. The data dir is `$TEST_TMPDIR/<name>.k8s/etcd_data`. It belongs to
  one test, is never reopened, and Bazel deletes it. If etcd or the host
  crashes, the test fails either way.
- **Why the default.** The failure it fixes, `etcdserver: request timed out`
  during `_apply_manifests`, happens after readiness, so no timeout can
  absorb it. It shows up exactly on the loaded hosts where nobody thought to
  set an opt-in. Every envtest etcd that `kubernetes.version()` downloads has
  the flag (checked with `etcd --help`: 3.5.10 for 1.29, 3.6.6 / 3.6.8 /
  3.7.0 for 1.35 / 1.36 / 1.37; the flag arrived in etcd 3.5.0).
- **Older etcd.** A `kubernetes.system()` etcd may be older and would
  refuse the unknown flag. When the flag is wanted, `_etcd_extra_flags` runs
  `etcd --help` once per launch and adds `--unsafe-no-fsync` only if the help
  text lists it. Otherwise it logs that etcd runs with fsync.
- **Why an opt-out.** It is there for anyone who wants etcd's normal
  durability path under test, for example while debugging etcd itself.

### Admission: `RULES_K8S_MAX_SERVERS`

This follows rules_kind v0.3.0's cluster slots (`RULES_KIND_MAX_CLUSTERS`).
A launcher takes one of `RULES_K8S_MAX_SERVERS` slots before the TLS
bootstrap: `slot-<i>` files in `RULES_K8S_SLOT_DIR`, each locked with a
non-blocking `flock` and polled every second. The TLS bootstrap is four RSA
key generations, CPU work that a loaded host should also queue. The holder
writes its pid and `$TEST_TARGET` into the slot file. A waiting launcher logs
those holders once a minute. The pid is as seen inside the holder's sandbox
PID namespace. Slot files are mode 0666, so a directory shared between users
works. With `RULES_K8S_MIN_FREE_MB`, the launcher also waits, after taking
the slot, until `MemAvailable` in `/proc/meminfo` reaches that value. The
wait has no timeout of its own; the test's timeout bounds it.

Where the design departs from rules_kind:

- **Who holds the lock.** rules_kind keeps its slot fd private to the
  launcher, which lives as long as the cluster. Here, test mode `execve`s
  into the test binary, and Python opens fds close-on-exec, so a private fd
  would free the slot just as the test starts. The slot fd is therefore made
  inheritable. It survives the `execve`, and it is passed (`pass_fds`) to
  etcd and kube-apiserver, the processes the limit is about. A flock is
  released when the last fd on it closes. So the slot stays taken until the
  launcher (or the test binary), etcd and kube-apiserver have all exited, by
  any means, SIGKILL included. A server that outlives its test still counts.
  The controller subprocess does not get the fd (the default
  `close_fds=True`); it is not a server.
- **Default directory: `/dev/shm/rules_kubernetes-<uid>/slots`, not
  `$XDG_RUNTIME_DIR`.** rules_kind's tests run unsandboxed, because they
  need a container runtime. rules_kubernetes tests normally run in
  `linux-sandbox`. Inside it, `/run/user/<uid>` is mounted read-only and
  `/tmp` is private to the test (verified with Bazel 9.3). `/dev/shm` is the
  host-shared directory that Bazel leaves writable. Every launcher of every
  Bazel server, sandboxed or not, therefore meets in the same directory. The
  parent directory is created 0700. Because `/dev/shm` is world-writable,
  the launcher refuses a parent directory that another user owns or that
  others can write. Without `/dev/shm` (macOS), the default is
  `$XDG_RUNTIME_DIR/rules_kubernetes`, else the temp directory. If the
  directory cannot be created, the error names `RULES_K8S_SLOT_DIR`,
  `--sandbox_writable_path` and `RULES_K8S_MAX_SERVERS=0`.
- **Default limit: the usable CPU count (`sched_getaffinity`), at least
  2.** rules_kind defaults to 2 because a kind cluster costs gigabytes. An
  envtest server costs a few hundred MB and mostly idles after startup.
  Bazel's `--local_test_jobs` also defaults to the CPU count, so one Bazel
  server alone is never throttled by the default. That keeps the default
  behavior for the common case, while N Bazel servers together are held to
  one server's worth of API servers instead of N times as many. Hosts that
  need more or less set the variable; `0` turns the limit off.
- **Invalid values fail** rather than fall back to the default with a
  warning (rules_kind's behavior), consistent with the timeouts above.

**CRDs are Established before anything uses them** (#5, item 4).
`_apply_manifests` returns the CRD names from `kubectl apply`'s
`customresourcedefinition.apiextensions.k8s.io/<name> ...` lines, and
`_wait_crds_established` polls each with `kubectl get crd -o jsonpath=` for
`Established=True` before the namespace, controller or test start. Polling
rather than `kubectl wait --for=condition=Established`, which exits 1 ("<nil>
is of the type <nil>") while a CRD has no conditions yet: that is why
consumers carried their own retry loops. Budget
`RULES_K8S_CRD_ESTABLISHED_TIMEOUT` (30 s); manifests without CRDs skip the
wait.

## Per-cluster paths (v0.7.0, rules_kind#25)

Up to v0.6.1 every launcher wrote `$TEST_TMPDIR/kubeconfig`,
`$TEST_TMPDIR/pki/`, `$TEST_TMPDIR/etcd_data`, `etcd.log` and
`apiserver.log`. Two `kubernetes_server` targets in one test therefore shared
them: the second launcher deleted the first's etcd data dir (etcd panicked,
"failed to create WAL"), re-bootstrapped the TLS files under a running
API server, and the last kubeconfig written won. A rules_kind `kind_cluster`
in the same test overwrote the same kubeconfig.

- **Paths.** Everything is named after the target: `<name>.kubeconfig`, and
  `<name>.k8s/` holding `pki/`, `etcd_data/`, `etcd.log`, `apiserver.log` and
  the controller's ready file. `<name>.env` already was. The env file's (or
  the test's) `KUBECONFIG` names the kubeconfig; consumers should read it
  rather than build the path. This changes a documented path, hence a minor
  version.
- **Claim.** Two targets with the same name (`//a:c`, `//b:c`) in one test
  would still collide, so the launcher first claims `$TEST_TMPDIR/<name>.claim`:
  a complete JSON file (`label`, `pid`, `rule`) linked into place, which
  fails if the file exists. If the holder's pid is alive, the launcher exits 1
  before resolving a binary or writing anything, naming both labels. A claim
  whose pid is gone (a launcher restarted within the test) is taken over. The
  label reaches the launcher as `RULES_K8S_TARGET_LABEL` from the rule's
  wrapper, the name as `RULES_K8S_TARGET_NAME`. A `kubernetes_test` keeps its
  claim through the `execve` (same pid).
- **Tests.** `launcher_unit_test` covers the claim (a live holder refuses a
  second claimant through the real entry point, with no files written;
  different names coexist; a dead holder's claim is taken over).
  `two_clusters_test` runs two servers in one test and checks that each
  kubeconfig points at its own API server and a namespace created through one
  is invisible through the other, then starts `//tests/samename:two_a_svc`
  and checks that it is refused.

## Known limitations and non-goals

- **No actual pod execution.** There is no kubelet. Pods never transition to
  `Running` unless kwok (Phase 2) is used to simulate the transition.
- **`kubernetes_test` stays independent** of `kubernetes_server`. The tight
  server+controller+exec coupling is its key value.
- **Target name collision.** Two `kubernetes_server` targets with the same local
  name in different packages write to the same `$TEST_TMPDIR/<name>.env`. Use
  unique target names within a test run.
- **TLS cert generation.** The launcher requires `openssl` in `PATH`. It is
  present on all supported Linux and macOS platforms.
- **Windows not supported.** No pre-built binary source; PRs welcome.
- **darwin tarball checksums are placeholders** until real SHA-256 values are
  pinned in `extensions.bzl`.
- **Controller readiness** is heuristic: the launcher polls for a
  leader-election lease by default. Controllers that do not use leader election
  need a custom readiness probe (configurable via the `ready_probe` attribute
  of `kubernetes_controller`).
